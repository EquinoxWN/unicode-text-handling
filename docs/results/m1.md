## Analyze

- **Normalization** is not where the built-in APIs fail: all three pass all 19,074 cases in all four
  forms, on runtimes at Unicode 15.0, 16.0 and 17.0.
- **Length and splitting** is: a "one code point per character" split gets 250 of 602 grapheme cases
  right and a UTF-16 split 220. `len()` in Python, `.length` in JavaScript and `length()` in Java are
  these naive counts (the family emoji is 7 code points, 11 UTF-16 units, 25 UTF-8 bytes, 1 character).
- **Python** has no grapheme segmenter in its standard library; this repo's 15.0.0 implementation
  passes all 602 cases.
- **Node.js 24** fails one 15.0.0 case: `U+2701 ZWJ U+2701` is one cluster in 15.0 but two in 17.0,
  because U+2701 is no longer Extended_Pictographic. Its segmenter also counts the Devanagari sample
  'नमस्ते' as 3 characters instead of 4 (rule GB9c, Unicode 15.1). Both are recorded in
  `spec/vectors/known-deviations.tsv`; they are version differences, not bugs.
- **Collation:** binary order (code points or UTF-16) keeps 81% of the DUCET sample's pairs in order;
  the JDK root `Collator` is barely better (82%); ICU's `Intl.Collator` keeps 99.8%. Which of ICU's 22
  out-of-order pairs come from CLDR root differing from the DUCET and which from Unicode 17 vs 15.0
  data has not been analysed yet (M3).
- **Encoding samples** (15, hand-checked) give the same byte, UTF-16 and code point counts in all
  three languages; grapheme counts agree except the documented Devanagari case on Node.js 24.

## Improve

- A Java CLI defect found by the tests: `--vectors` pointing at a missing directory threw an
  uncaught `VectorException` instead of exiting with code 1. Fixed in `App.java`; the CLI test covers it.
- Hand mutation found that no test corrupted only column c3 of a normalization case; a test where
  the normalizer is wrong on exactly one column (each of c1..c5) now runs in all three languages.

## Reproduce

`python spec/fetch_ucd.py` downloads the five pinned files (SHA-256 in `spec/fetch_ucd.py`) into
`data/ucd/15.0.0`; `python spec/generate_vectors.py` rebuilds `spec/vectors` and the Python table.
No models or random seeds are involved.
